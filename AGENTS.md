## What this repo is

fxbot is a TypeScript monorepo of four npm workspaces: `packages/sdk` (`@fxbot/sdk`, the agent system around [libfx](https://fx.sh/docs/lib), plus `@fxbot/sdk/client` for UIs), `packages/server` (the HTTP API over the SDK), `packages/ui` (the PWA), and `packages/website` (the public site and its docs, static pages that import none of the other three). v1 is built: bot profiles and the chat UI, and so are [provider logins](docs/_completed/phases/provider-logins.md), the [library](docs/_completed/phases/library.md), the [installable app](docs/_completed/phases/pwa.md), remote [MCP servers](docs/_completed/phases/mcp.md), [releases](docs/_completed/phases/releases.md) (tagged versions, `setup.sh`, updates from Settings, and numbered migrations), [plugin search](docs/_completed/phases/addons.md) (a mirror of GitHub's MCP registry, a page per entry, and marks and updates for installed servers), and [skills](docs/_completed/phases/skills.md) from fxbot's list and skills.sh, read by bots through a `skill` tool. A release install runs as [containers](docs/_completed/phases/containers.md): fxbot's image and pgvector's Postgres from one compose file (`deploy/`), under podman or docker, with a host `fxbot` command that carries out updates the app asks for. Each bot keeps [memories](docs/_completed/phases/memories.md), found by words and by meaning with vectors from a local embedder in the same compose file or a provider's. A plugin is the one kind of thing an owner installs, and carries any mix of code, MCP servers, and skills ([one kind of plugin](docs/_completed/phases/one-kind-of-plugin.md)); by default only fxbot's vetted ones show, each with an [icon](docs/_completed/phases/plugin-icons.md) of its own, drawn from who made it and its name, and listed with a page each in fxbot.sh's [plugin directory](docs/_completed/phases/plugin-directory.md). A plugin's code changes the app itself through the [plugin API](docs/_completed/phases/plugins.md): hooks into turns and tool calls, tools, routes, tables in a schema of their own, settings, and places in the page. fxbot's own, [chat rooms](docs/_completed/phases/chat-rooms.md), where bots tag each other, and the [computer](docs/_completed/phases/computer.md), are in `plugins/`, outside the workspaces, and are added from GitHub like anyone's. The computer gives each bot a Linux machine in the machine's own podman or docker, run rootless for a user of its own by a script the owner runs once, with a [desktop](docs/_completed/phases/computer-v2.md) the owner watches and takes over, a shared terminal, and Chromium, which bots drive with agent-browser and agent-desktop. A room can have a computer its bots share, taking turns, from the chat-rooms-computer plugin ([a room's computer](docs/_completed/phases/chat-rooms-computer.md)), and plugins use one another through `fx.provide` and `fx.need`. Settings is a screen of tabs, each at its own address, with a tab for each plugin ([settings tabs](docs/_completed/phases/settings-tabs.md)), and a launch opens the [default bot](docs/_completed/phases/default-bot.md)'s chat when the owner picks one. A bot's chat starts over from a summary of it, by a provider switch or by `/fresh` ([fresh](docs/_completed/phases/fresh.md)), whose plugin is in `plugins/` too. Each night a bot can go over its day and keep what it learned as memories and skills, with a journal and Undo in its settings ([dreams](docs/_completed/phases/dreams.md)), from a plugin in `plugins/` as well, through `fx.memories` and `fx.skills.set`. A bot can run saved tasks on a schedule, in sessions of their own with everything it has, and tell the owner in its chat ([routines](docs/_completed/phases/routines.md)), from a plugin in `plugins/` too, on the owner's time zone in Settings › General, which plugins read with `fx.timeZone()`. A message to a working bot joins what it's doing, and **Stop** ends a turn. Bots message each other in their own chats, and the owner watches, with a budget for each conversation and real replies ([cross-bot messaging](docs/_completed/phases/cross-bot-messaging.md)), from a plugin in `plugins/` too. The owner decides what each bot does alone, by asking first, by a reviewer model, or by running everything, and a call that needs the owner waits at a card in the chat ([permissions](docs/_completed/phases/permissions.md)), from a plugin in `plugins/` as well. A plugin says the oldest fxbot it runs on, and fxbot keeps a list of what each release broke, so one that can't run shows **Unsupported**, and the rest carry on ([plugin compatibility](docs/_completed/phases/plugin-compatibility.md)). A new install walks through a pack of what most people want, **Essentials**, or plugins of the owner's own, then a provider and a first bot, and the pack stays at the top of **Browse** ([onboarding](docs/_completed/phases/onboarding.md)). A bot writes reports, guides, and plans to read outside the chat, in Markdown, or HTML in a sandboxed frame, kept in the library with every version ([pages](docs/_completed/phases/pages.md)), from a plugin in `plugins/` too. The owner and a bot both work on a page: ticks edit its text, an HTML page saves what it's given, a bot sends it data once the owner approves its exact text, and a page can draft a message for the owner to send ([pages v2](docs/_completed/phases/pages-v2.md)). Each bot has a look of its own: one of 32 shapes in soft color, with big dark eyes that carry a feeling, and things to wear cut to its outline, and it shows when it's working, waiting, finished, or asleep ([avatars](docs/_completed/phases/avatars.md)). Records live in Postgres, and so do the chats: libfx's sessions, through Workflow's Postgres World ([streams](docs/_completed/phases/streams.md)). There is no test suite or CI.

fxbot is a small core plus plugins, like [Pi](https://github.com/earendil-works/pi). The core is what every bot needs, what plugins plug into, and what fxbot needs to run. Everything else is a plugin that an owner adds only if they want it, carrying MCP servers, skills, or code. A plugin's code changes the app itself, through hooks and places of its own in the app. The other phase stubs describe future work. Do not report them as running behavior.

Later ideas live as one-page stubs in [docs/phases/](docs/phases/). Build one only when asked.

## Rules

- Prefer the smallest change that meets the task. Drop an older convention when it fights that.
- Before building a feature, ask: is it core, or a plugin? The default is plugin. Follow [Core or plugin](CONVENTIONS.md#core-or-plugin), and say which in the phase doc. When a plugin can't do what it needs, widen the plugin API with the smallest hook it needs, not the feature.
- `main` holds releases, and updates to the site between them. Commit to the open `release/<next version>` branch, never to `main`; the owner merges and releases ([README: Releasing](README.md#releasing)).
- Commit as you go. When a piece of work is done and its checks pass, commit it on the open release branch, with a message that says what changed, so the owner only has to push. Keep unrelated changes in separate commits. Don't push, merge, or tag unless the owner asks.
- A change that removes or breaks something in the plugin API adds a line to `packages/sdk/src/plugin-breaks.json`, and a note under `## Unreleased` ([plugin compatibility](docs/_completed/phases/plugin-compatibility.md)). A plugin in `plugins/` that starts using something newer raises its `minFxbot`.
- A schema change is a new numbered file in `packages/sdk/src/migrations/`. Never edit or remove one that has shipped in a release. Note it under `## Unreleased` in `CHANGELOG.md`, for the release's Before upgrading list.
- The stack is Vite, React, shadcn/ui, and a tiny Node server around libfx. Do not add Next.js, the Vercel AI SDK, a second agent runtime, or Hermes Agent.
- Agent logic, storage, and input checks belong in `@fxbot/sdk`. The server only adds HTTP. The UI imports only `@fxbot/sdk/client`, never the SDK's main entry.
- Never put a secret in the page or in `@fxbot/sdk/client`. Keys and tokens live only on the server, sealed in Postgres by the SDK. The page sends a key once and never receives one. Vite reads no `.env`.
- libfx behavior comes from the installed package or the published docs. Say what you could not verify.
- This is a public repo. Do not add private hostnames, machine names, personal subscriptions, home-directory paths, or private project names.
- Write "Hackers in the Loop" in full if that name is needed.

## Checks

Run these from the repository root after `npm install`, with Node 22.18 or newer:

- `npm run typecheck` runs `tsc --noEmit` in each package, with that package's own `tsconfig.json`, then over the server code in `plugins/`, then `scripts/check-plugins.mjs`, which checks each plugin's `minFxbot` against the next release.
- `npm run build` builds the page and service worker into `packages/ui/dist/`. It does not typecheck.
- `npm run build-site` builds the website into `out/` with Astro and Starlight, and checks its links. It needs Node 22.22 or newer. Its docs are Markdown in `packages/website/src/content/docs/docs/`, and the SDK's pages, for people who build their own apps on `@fxbot/sdk`, in `packages/website/src/content/docs/sdk/`: one [Diátaxis](https://diataxis.fr) kind per page, each listed in `src/sidebar.ts`. The home page is React, in `src/home.tsx`. The changelog page and the variables table come from `CHANGELOG.md` and the README. `npm run dev -w @fxbot/website` serves it as you edit.
- Add shadcn components from `packages/ui`: `npx shadcn@latest add <name>`.
- `podman build .` (or `docker build .`) builds fxbot's image from the `Dockerfile`. `bash -n setup.sh deploy/fxbot` checks the shell scripts' syntax.
- A plugin's `page.js` is built from its `page.jsx` with rolldown, by the command in its README. Commit both.
- `node scripts/blob-data.mjs` writes `packages/ui/src/blob-data.ts`, and copies it and `blob-draw.ts` to the site. Run it after changing a shape, a color, or `blob-draw.ts`.
- `git diff --check` checks whitespace on tracked changes. New files need a separate look; untracked files are outside that diff.

There are no automated tests. Behavior is checked by hand, in a browser or with `curl`, as the milestones and checklists in [docs/_completed/v1-plan.md](docs/_completed/v1-plan.md) and [docs/phases/](docs/phases/) describe. `npm run server` needs Postgres (a checkout's comes from `deploy/compose.dev.yaml`), `FXBOT_DATABASE_URL`, and `FXBOT_SECRET_KEY_FILE`, from the environment or `.env` (see the README). Point checks at a disposable database and `FXBOT_DATA`, and at another port with `FXBOT_PORT`. Check the release compose file with another `COMPOSE_PROJECT_NAME`, `FXBOT_PORT`, and `FXBOT_ROOT`, so it stays clear of a real install on the same machine. Do not claim a check passed unless it ran.
